# 01 — Understand the repository map

## Learning goal

After this module you should be able to answer three questions before editing:

1. Where does this change belong?
2. What will happen to the file after it is changed?
3. Who or what must review it?

## Repository versus website

A **repository** is the project folder tracked by Git. It contains source files, instructions, history and automation.

A **website** is the result produced from some of those files. Visitors do not receive the TypeScript source or Markdown front matter directly. They receive the static files generated into `dist/` and published by GitHub Pages.

That distinction explains two common surprises:

- Editing a source file does not change the public site until the change is built and deployed.
- Editing `dist/` does not permanently change the site because the next build recreates it.

## The publishable structure

```text
ospo-landing-page/
├── .github/                 GitHub review, issue and automation configuration
├── src/                     Website source code and Markdown content
│   ├── assets/              Images imported by the application
│   ├── content/posts/       Markdown articles
│   ├── content.ts           Post parsing and fixed news/report data
│   ├── main.ts              Routes, page rendering and interactions
│   └── style.css            Site-wide design and responsive layout
├── public/                  Files copied to the built site as-is
├── scripts/                 Local/CI validation scripts
├── presentation.html        Long self-contained presentation
├── presentation-short.html  Short self-contained presentation
├── index.html               HTML entry point for the application
├── package.json              Project identity, scripts and dependencies
├── package-lock.json         Exact dependency versions for repeatable installs
├── tsconfig.json             TypeScript rules
├── vite.config.ts            Build inputs and deployment base path
└── repository documents      README, contributing, security, governance, licence
```

## The most important files

| If you want to… | Start here | Why |
| --- | --- | --- |
| Add or correct an article | `src/content/posts/*.md` | Posts are discovered automatically at build time |
| Change the home/story/start/library page structure | `src/main.ts` | It contains the route and HTML rendering functions |
| Change post parsing or fixed news/reports | `src/content.ts` | It turns Markdown into post data and stores fixed page data |
| Change colours, spacing or responsive layout | `src/style.css` | The whole application uses this global stylesheet |
| Change the HTML shell or metadata | `index.html` | It provides `<html>`, `<head>` and the `#app` mount point |
| Change the production build | `vite.config.ts`, `package.json` | Vite builds the application and the two presentations |
| Change content checks | `scripts/validate-content.mjs` | `npm test` runs this script |
| Change the long or short deck | `presentation.html`, `presentation-short.html` | These files contain their own HTML, CSS and JavaScript |
| Change deployment or security automation | `.github/workflows/*.yml` | GitHub runs these files outside your computer |
| Change who must review a path | `.github/CODEOWNERS` | GitHub uses this to request reviews |
| Explain a repository process | `README.md`, `CONTRIBUTING.md`, `GOVERNANCE.md` | These are the human operating instructions |

## What happens to each kind of file?

### Source files

Files under `src/` are read by Vite. TypeScript is checked by `tsc`, CSS is bundled, and imported assets are fingerprinted into the build output.

### Markdown posts

Files under `src/content/posts/` are imported by this line of the application:

```text
import.meta.glob('./content/posts/*.md', { eager: true, query: '?raw', import: 'default' })
```

You do not add a post to a registry by hand. Create a `.md` file with valid front matter, and the build discovers it.

### Public files

Files under `public/` are copied to the output without being processed as application modules. `public/robots.txt` is therefore available as a root-level public file. The existing SVG favicon is also a public asset, although the current `index.html` does not explicitly link it.

### Presentations

The presentations are standalone HTML documents. Their CSS and JavaScript are embedded in the files. They do not import the application’s `src/main.ts` or `src/style.css`.

They are nevertheless listed as Vite build inputs in `vite.config.ts`, so `npm run build` includes them in `dist/`.

### Generated and local files

- `dist/` is generated by `npm run build`; do not edit or commit it.
- `node_modules/` is created by npm; do not edit or commit it.
- `.tmp/` and `.memories/` are local working/evidence areas; do not publish them.
- `package-lock.json` is generated and maintained by npm. Do not hand-edit it as a normal content file.

## How the browser receives a page

The main application starts in `index.html`:

1. The browser loads the HTML document.
2. The document contains `<div id="app"></div>`.
3. The module script loads `src/main.ts` through Vite.
4. `main.ts` imports the CSS and content data.
5. `main.ts` writes the current page HTML into `#app`.
6. `main.ts` attaches the menu and library-filter interactions.

This is why `index.html` is small while most visible page content is in `src/main.ts` and Markdown.

## The route map

The site uses the URL fragment after `#`, sometimes called a **hash route**:

| URL fragment | Page |
| --- | --- |
| `#/` or `#/home` | Home page |
| `#/story` | Our story |
| `#/start` | Start here |
| `#/library` | Content library |
| `#/post/<slug>` | One Markdown post |

Hash routes are useful on GitHub Pages because the web server does not need to know how to rewrite every route to `index.html`.

A route is not a folder. `#/library` does not mean that a `library/` directory exists. It is a value read by `getRoute()` in `src/main.ts`.

## Generated output and the base path

The same source can be used as:

- a project site at `https://owner.github.io/repository/`; or
- an organization site at `https://owner.github.io/`.

`vite.config.ts` reads `BASE_PATH`. The deployment workflow calculates the appropriate value. Local development normally uses `/`; a project-site simulation can use a path such as `/ospo-landing-page/`.

Most internal application links use hash routes such as `#/library`, so they do not need a hardcoded repository path. Avoid changing them to root paths such as `/library`.

## File-to-owner thinking

Before opening a pull request, ask:

- Is this a public claim, a code change, a design change or an operational change?
- Does `CODEOWNERS` cover the path?
- Does the change need OSPO/editorial, project, legal/IP, security or accessibility review?
- Is the evidence public and linkable, or is it only local working material?
